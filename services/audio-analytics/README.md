# Аудиоаналитика — сервис записи и разбора смен

Сервис принимает запись рабочего дня с ресепшена студии (приложение Tauri
на компьютере у стойки), распознаёт речь (русский / грузинский / английский)
и с помощью Claude разбирает смену: делит день на разговоры, оценивает их по
метрикам владельца, подводит итог дня и считает стоимость разбора.

Это перенос речевой аналитики из отдельного проекта `audio-analitics`
(FastAPI + Celery + Redis) на портал. Перенесено только то, что касается
записанной смены: приём записи, пайплайн разбора, стоимость, плеер, обновления
приложения. Скрипты, CRM, логины сотрудников прежнего проекта сюда не
переехали — на портале свои «Скрипты LS», вход и «Пользователи и роли».

Схема базы — `db/migrations/2026-10-30_audio_analytics.sql` (таблицы `aa_*`,
права `audio.own` / `audio.view` / `audio.manage`, RPC админки). Интерфейс —
раздел «Аудиоаналитика» админки: он читает таблицы через RLS и зовёт RPC
(`aa_recording_process`, `aa_recording_delete`, …), а к сервису обращается
только за тем, чего база не умеет: ссылкой на запись смены, загрузкой сборки
приложения и состоянием сервиса.

## Устройство

```
[Приложение на ресепшене]  Opus-куски по 5 мин ──► API ──► хранилище (/data или S3)
                                                    │
[Админка] ── RPC aa_recording_process ──► aa_recordings.status = 'queued'
                                                    │
                    воркер (тот же контейнер) ◄─────┘  for update skip locked
   ffmpeg → Silero VAD → ElevenLabs Scribe → Claude: разговоры → метрики → итог дня
                                                    │
                       aa_dialogs, aa_dialog_turns, aa_metric_evaluations,
                       aa_day_summaries, стоимость в aa_recordings
```

* **Один контейнер, два процесса** (`start.sh`): API (`uvicorn app.main:app`)
  и воркер (`python -m app.worker`). Умер любой — контейнер завершается, и
  Docker перезапускает его целиком.
* **Очередь — сама таблица смен**, без Redis и Celery. Воркер забирает самую
  давнюю смену в статусе `queued` (`for update skip locked`), переводит в
  `processing` и разбирает. Смены, брошенные в `processing` перезапуском
  (передеплой, нехватка памяти), при старте воркера возвращаются в очередь с
  пояснением «разбор прерван перезапуском сервиса — запущен заново»; на
  третьем обрыве подряд смена уходит в «Ошибку» — иначе смена, которая сама
  роняет воркер, крутилась бы вечно и каждый раз платила бы за распознавание.
* **Сигнал жизни** — `aa_service_state` (`worker`: pid, время старта,
  текущая смена, версия), раз в ~30 с, в том числе посреди многочасового
  разбора. «Настройки» админки видят его через `GET /api/staff/status`.
* **Стирание файлов** — очередь `aa_storage_purge` (удалённые смены и сборки:
  строки базы удаляются сразу, файлы — воркером). Стираются только префиксы
  `recordings/<uuid>/` и `app-releases/<платформа>/<версия>/…` — короткий или
  чужой префикс воркер не тронет.
* **Срок хранения** — раз в сутки (см. «Приватность»).

Разбор, как и прежде, **запускается вручную** из админки: приложение
закрывает смену («ждёт запуска разбора»), а платить за распознавание пустых
дней, дублей и проверок оборудования никто не хочет. «Пересчитать» берёт
сохранённую расшифровку и за распознавание второй раз не платит;
«Распознать заново» (`process_full`) — платит.

Экономия перенесена без изменений: сервисные и короткие (< 4 реплик)
разговоры по метрикам не оцениваются, все метрики разговора — одним
запросом, сегментация дня — блоками по паузам, стоимость — по тарифу каждой
модели с кэшем (`app/pipeline/cost.py`). Строка под статусом «Готово»
объясняет итог: сколько разговоров и метрик, сколько оценок сработало, что
пропущено, сколько стоило.

## Эндпоинты

### Приложение на ресепшене (контракт прежнего сервера, без изменений)

Заголовки: `X-App-Key` (общий ключ приложения, `APP_KEY`) и
`X-Location-Id` (выбранная точка продажи, должна быть открыта).

| Метод и путь | Что делает |
|---|---|
| `GET /api/recordings/locations` | Открытые точки продажи (`id`, `name`, `address`) — только по `X-App-Key` |
| `GET /api/recordings/employees` | Активные менеджеры (`id`, `location_id` = точка устройства, `full_name`, `role: "manager"`, `active`) |
| `POST /api/recordings/start` `{date, employee_id}` | Продолжить незакрытую смену точки за эту дату или открыть новую |
| `PUT /api/recordings/{id}/segments/{idx}` multipart `file` | Кусок записи; повтор того же номера перезаписывает его (до `MAX_SEGMENT_MB`) |
| `POST /api/recordings/{id}/finish` `{total_segments}` | «Ждёт запуска разбора»; не хватает кусков или смена уже закрыта — 409 |
| `GET /api/app/update/{platform}/{arch}/{version}` | Апдейтер Tauri: 204 — обновлять нечего, 200 — манифест со ссылкой на архив |

409 приложение понимает как «смена закрыта на сервере» и перестаёт
дозагружать куски — смысл кода сохранён.

### Админка

`Authorization: Bearer <токен входа Supabase>`. Токен проверяет GoTrue
(`GET {SUPABASE_URL}/auth/v1/user`, кэш на минуту по хэшу токена), права —
функции базы: `aa_recording_visible(id)` и `aa_has(uid, 'audio.manage')`.
CORS — для `CORS_ORIGINS`.

| Метод и путь | Права | Что делает |
|---|---|---|
| `GET /api/staff/audio/{recording_id}` | смена видна (`audio.view` / `audio.manage` / своя) | `{url, expires_in_s}` — ссылка на склеенную запись смены. Чужая или несуществующая — 404 (не 403), аудио стёрто по сроку — 410 |
| `POST /api/staff/releases` multipart: `archive`, `signature_file` или `signature`, `version`, `platform`, `notes` | `audio.manage` | Выложить сборку приложения: версия — из `Info.plist` архива (иначе поле), дубль версии — 409, до 300 МБ |
| `GET /api/staff/status` | `audio.manage` | Версия, хранилище, что настроено (ASR, модель, ключ приложения), сигнал жизни воркера, очередь, срок хранения, модели |

Снять сборку с публикации, поправить заметки и удалить её админка может
сама (RLS); удаление ставит архив в очередь стирания триггером в базе.

### Файлы и служебное

* `GET /files/{token}` — файл локального хранилища по подписанной ссылке
  (HMAC-SHA256, `FILES_URL_SECRET`, срок — `PRESIGNED_URL_TTL_S`). Поддерживает
  `Range`: плеер админки перематывает 12-часовую запись, не скачивая её.
  Подпись не сходится или срок вышел — 403, файла нет — 404.
* `GET /health` — для HEALTHCHECK контейнера.

## Переменные окружения

Полный список с пояснениями — [`.env.example`](.env.example). Главное:

| Переменная | Зачем |
|---|---|
| `DATABASE_URL` | База портала (та же, что у админки); `postgres://` и `postgresql://` подходят оба |
| `PUBLIC_URL` | Внешний адрес сервиса — из него строятся ссылки на файлы |
| `CORS_ORIGINS` | `https://admin.base40.fit` |
| `STORAGE_BACKEND` | `local` (по умолчанию, `/data`) или `s3` (+ `S3_*`) |
| `FILES_URL_SECRET` | Ключ подписи ссылок для `local` — длинная случайная строка |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | Проверка входа сотрудников через GoTrue |
| `APP_KEY` | Ключ приложения на ресепшене — **тот же**, что у прежнего сервера |
| `ELEVENLABS_API_KEY`, `ANTHROPIC_API_KEY` | Распознавание и модель |
| `PRICE_ASR_PER_HOUR_USD` | Фактическая цена часа распознавания — по умолчанию ориентировочная |
| `AUDIO_RETENTION_DAYS` | Срок хранения аудио, по умолчанию 60 |

Переменные разбора (`LLM_*`, `PRICE_*`, `VAD_*`, `CONVERSATION_GAP_S`,
`STALE_PROCESSING_S`) — те же, что у прежнего проекта: значения переносятся
как есть. Чего не хватает, сервис пишет в журнал при старте.

## Деплой в Coolify

Новый ресурс из этого репозитория, ветка `main`:

| Настройка | Значение |
|---|---|
| Build Pack | Dockerfile |
| Base Directory | `/` (контекст сборки — корень репозитория) |
| Dockerfile Location | `/services/audio-analytics/Dockerfile` |
| Watch Paths | `services/audio-analytics/**` |
| Порт | `8000` |
| Домен | `https://audio.base40.fit` |
| Постоянное хранилище | том на `/data` (иначе передеплой стирает все записи) |
| Переменные | по `.env.example` |

Миграцию `2026-10-30_audio_analytics.sql` выполняет админка при своём
старте, поэтому сначала выкатывается админка (схема), потом — сервис.

Образ: `python:3.12-slim` + ffmpeg, модель Silero VAD скачивается при сборке
(первый рабочий день не зависит от доступности GitHub). HEALTHCHECK —
`/health` на Python (curl в образе нет). Сигнал `docker stop` `start.sh`
передаёт обоим процессам; разбор, прерванный посередине, вернётся в очередь
при следующем старте.

Размер: двенадцатичасовая смена — около 170 МБ Opus (сегменты) + столько же
склейки; за 60 дней на 2–3 точки — порядка 40–60 ГБ на диске сервера.

## Приложение на ресепшене

Приложение (`desktop/` прежнего проекта) работает с сервисом без пересборки
— меняется только адрес сервера:

* в настройках приложения, раздел «Для настройщика» → адрес сервера
  `https://audio.base40.fit`; ключ приложения — тот же (`APP_KEY`);
* или выпустить сборку с вшитым новым адресом
  (`AA_SERVER_URL=https://audio.base40.fit AA_APP_KEY=… npm run build:mac`) и
  выложить её **на прежнем** сервере как обновление: приложения обновятся
  сами и дальше пойдут на новый адрес (если адрес не переопределён в
  настройках машины).

Точку продажи приложение помнит по id. Перенос сохраняет id точек, поэтому
выбор остаётся верным; исключение — точка, которую на портале уже завели
под тем же названием до переноса (смены прежней точки достаются ей): на
таком компьютере точку нужно выбрать заново.

Прежняя схема со своим ключом на каждое устройство (`X-Device-Key`,
`DEVICE_API_KEYS`) не перенесена: такие машины надо перевести на общий
ключ и выбор точки.

Склеенная запись — Ogg Opus: Safari её не играет, отчёты слушают в Chrome,
Edge или Firefox.

## Перенос из прежнего проекта

```bash
# в контейнере сервиса (Coolify → Terminal) или локально с DATABASE_URL портала
python -m cli.import_legacy --old-database-url "postgres://…прежняя база…" --dry-run
python -m cli.import_legacy --old-database-url "postgres://…" --copy-audio
```

1. Выкатить админку (миграция) и сервис; `APP_KEY` — как у прежнего сервера.
2. `--dry-run` — посчитать, что переносится, ничего не меняя.
3. Перенос с `--copy-audio`: файлы копируются из прежнего R2 (`OLD_S3_*`) в
   хранилище сервиса потоком, уже скопированные пропускаются. Аудио смен
   старше `AUDIO_RETENTION_DAYS` не копируется — только расшифровки.
4. Переключить приложения на новый адрес (после закрытия смен).
5. Запустить перенос ещё раз: он идемпотентен (по id) и доберёт смены,
   пришедшие на прежний сервер в промежутке. Уже перенесённые строки не
   обновляются — смену, которую успели разобрать на прежнем сервере после
   первого переноса, на портале проще «Пересчитать».
6. Остановить прежний сервер.

Что и как переносится (подробно — в шапке `cli/import_legacy.py`): точки,
менеджеры (без учётных записей — связать с человеком портала в
«Менеджерах»), смены, сегменты, расшифровки, разговоры, реплики, метрики,
оценки, итоги смен, история промптов `dialog_segmentation` и `daily_summary`,
«согласен / не согласен» (только с метрикой; автор — подписью), договорённости
(автор — подписью), сборки приложения. Стартовые метрики портала
заменяются прежними, если по ним ещё нет оценок; стартовые версии промптов —
историей прежних. Смены «в очереди / в обработке» переносятся как «ждёт
разбора» — воркер не начнёт тратить деньги без спроса. В конце — сводка по
таблицам.

## Приватность и срок хранения

Аудиозапись в помещении регулируется законом Грузии «О защите персональных
данных» (в силе с 01.03.2024): нужны табличка-уведомление для клиентов,
письменное согласие сотрудников, документированная политика хранения и
ограничение доступа. Формулировки согласовать с юристом. В приложении есть
кнопка «Пауза» для личных разговоров.

Срок хранения соблюдает сам сервис: раз в сутки у смен старше
`AUDIO_RETENTION_DAYS` дней (кроме записываемых, ждущих и идущих в разбор)
стираются сегменты и склеенная запись, в смене ставится `audio_purged_at`.
Остаются разбор, текст разговоров и расшифровка (`transcript.json`) — по ней
смену можно пересчитать по новым метрикам; «Распознать заново» у такой смены
отказывает понятным текстом, не трогая готовый отчёт. Строки `aa_segments`
остаются как запись о том, что и когда было загружено. При `STORAGE_BACKEND=s3`
lifecycle-правило бакета можно не настраивать (или поставить на больший срок
как страховку).

Личные разговоры (`irrelevant`) классифицируются, но их текст и реплики не
сохраняются. Ссылки на записи — временные и выдаются только тем, кому смена
видна по правам портала.

Пересчёт смены пересоздаёт разговоры, поэтому голоса «согласен / не
согласен» по прежним оценкам уходят вместе с ними (каскад в схеме), а у
договорённостей обнуляется ссылка на разговор.

## Разработка и тесты

```bash
cd services/audio-analytics
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
pytest                                   # модульные: без сети и базы

# с базой портала (схему собирает: bash db/test/build-schema.sh <url>)
TEST_SCHEMA_DATABASE_URL=postgres://postgres:postgres@localhost:5432/base40_test pytest
# + перенос: пустая база со схемой прежнего проекта (его миграции 001–009)
TEST_LEGACY_DATABASE_URL=postgres://…/aa_legacy_test
# + настоящий Silero VAD на сгенерированном ffmpeg аудио
VAD_MODEL_PATH=/путь/silero_vad.onnx
```

Тесты с базой работают в одной транзакции и откатывают её — база остаётся
чистой. Распознавание, модель и проверка входа подменены; аудио настоящее
(ffmpeg, Ogg Opus).

Запуск без Docker: `.env` по образцу `.env.example` (`STORAGE_DIR=./data`),
затем `bash start.sh` (нужны `python` и `uvicorn` из venv в `PATH`).
