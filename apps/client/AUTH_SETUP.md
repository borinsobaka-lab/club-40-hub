# Настройка почтовой авторизации (noreply@base40.fit)

Письма разделяются **по приложению, а не по человеку**. Админка и клиентское
приложение — разные сущности: один и тот же человек может быть и
администратором, и клиентом, и в клиентском приложении он должен идти
клиентским путём.

Отправку писем Supabase делегирует нашему серверу (Send Email Hook →
`https://admin.base40.fit/api/auth-email`), который смотрит, из какого
приложения пришёл запрос, и шлёт через Resend:

- вход в **клиентское приложение** (app.base40.fit) → **4-значный код**,
  без единой ссылки — даже если это администратор;
- вход в **админку** (admin.base40.fit) → **ссылка авто-входа**, без кода;
- восстановление пароля и приглашения сотрудников — письма со ссылками
  (у клиентов паролей нет, эти сценарии только в админке).

Признак приложения — адрес возврата, который приложения передают явно. Если
распознать не удалось, отправляется код: ссылка авто-входа — это полный
доступ, и слать её «на всякий случай» нельзя.

Редактировать шаблоны в Supabase НЕ нужно — при включённом хуке они не
используются. Код обоих приложений готов; ниже — шаги настройки.

## Шаг 1. Resend

1. Домен `base40.fit` в Resend верифицирован (SPF + DKIM в Cloudflare DNS,
   статус Verified) — иначе письма не дойдут или упадут в спам.
2. Создать API-ключ: Resend → API Keys → Create (права Sending). Скопировать.

## Шаг 2. Секрет хука в Supabase

Dashboard проекта `lyvarbqquvgxufmqgyix` → **Authentication → Hooks** →
**Send Email Hook**:

1. Тип: **HTTPS**, URL: `https://admin.base40.fit/api/auth-email`.
2. Скопировать **сгенерированный секрет** (`v1,whsec_...`).
3. **ПОКА НЕ включать** (не сохранять Enabled) — сначала шаг 3.

## Шаг 3. Переменные в Coolify

Coolify → приложение **club40-admin** → Environment Variables, добавить две
runtime-переменные (галочку Build Variable НЕ ставить):

| Имя                      | Значение                          |
| ------------------------ | --------------------------------- |
| `SEND_EMAIL_HOOK_SECRET` | секрет из шага 2 (`v1,whsec_...`) |
| `RESEND_API_KEY`         | API-ключ из шага 1 (`re_...`)     |

Затем **Restart** приложения.

## Шаг 4. Включить хук

Вернуться в Supabase → Authentication → Hooks → Send Email → **Enable**.
Порядок важен: если включить хук до рестарта админки с переменными, письма
перестанут уходить вовсе (роут ответит 500).

## Шаг 5. Длина кода — 4 цифры

**Authentication → Sign In / Up → Email**: **Email OTP Length = 4**
(по умолчанию 6, приложение ждёт 4). OTP Expiration — 3600 сек.

## Шаг 6. Лимиты

**Authentication → Rate Limits**: поднять лимит писем до разумного
(например, 100/час) — с хуком отправка идёт через ваш Resend.

## Шаг 7. Проверка

1. Клиентское приложение, **почтой администратора** → «Получить код» →
   письмо от `CLUB 40 <noreply@base40.fit>` с 4 цифрами и без ссылок →
   вход работает. Это главная проверка: администратор в клиентском
   приложении — клиент.
2. Регистрация нового email → письмо «Добро пожаловать» с кодом; после
   входа профиль создан, имя/телефон на месте.
3. Админка → пароль → письмо «Вход в админ-панель» с кнопкой (без кода) →
   клик → вход.
4. Письма не в спаме.

Если письма перестали приходить: Coolify → club40-admin → Logs, искать
`[auth-email]`. Быстрый откат — выключить хук в Supabase (вернутся встроенные
письма Supabase с их шаблонами).

## Как это устроено (для справки)

Роут `src/routes/api/auth-email.ts` в репозитории админки проверяет подпись
вебхука (HMAC, standardized-webhooks); логика писем — `src/lib/auth-email.ts`,
покрыта тестами (`bun test`): решение принимается по хосту адреса возврата,
роли пользователя на письмо не влияют. Типы писем: signup (код), magiclink
(код клиенту / ссылка сотруднику), recovery (ссылка), invite (ссылка),
email_change (код). Секреты живут только в Coolify у админки — у клиентского
приложения секретов нет по-прежнему.

## Важное о безопасности (уже исправлено в коде)

Раньше OTP в клиентском приложении был бутафорией: код не проверялся, а вход
шёл по выводимому из email паролю — войти можно было под любым клиентом, зная
только его почту. Теперь вход только по настоящему коду. После настройки
стоит просмотреть Authentication → Users на предмет подозрительных аккаунтов,
созданных за время тестирования.
