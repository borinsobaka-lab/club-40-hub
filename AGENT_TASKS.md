# Задача S. 🔴 Переезд на self-hosted Supabase (2026-10-07)

База перенесена с облачного проекта `lyvarbqquvgxufmqgyix` на self-hosted
Supabase в Coolify (API `https://api.base40.fit`) 1:1. Код обоих приложений
переключён (`.env`), осталось окружение. Настройки Auth облачного проекта
(хук писем, redirect URLs, лимиты) НЕ переносятся вместе с базой — их нужно
задать заново переменными сервиса **auth** в ресурсе Supabase в Coolify.

1. **Coolify → club40-admin и club40-client → Environment Variables**:
   `VITE_SUPABASE_URL` = `https://api.base40.fit`,
   `VITE_SUPABASE_PUBLISHABLE_KEY` = значение из `.env` репозитория (`eyJ...`),
   обе с галочкой Build Variable. У club40-admin дополнительно
   `APP_SUPABASE_SERVICE_KEY` = service*role JWT self-hosted инстанса.
   `VITE_SUPABASE_PROJECT_ID` у club40-client можно удалить. Затем Redeploy
   обоих (VITE*\* вшиваются при сборке — простого Restart мало).
2. **Сервис auth (GoTrue)**, переменные:
   (в шаблоне Coolify часть из них проброшена через короткие имена —
   `SITE_URL`, `ADDITIONAL_REDIRECT_URLS`, `DISABLE_SIGNUP`; тогда менять их)
   - `GOTRUE_SITE_URL=https://admin.base40.fit`
   - `GOTRUE_URI_ALLOW_LIST=https://admin.base40.fit/**,https://app.base40.fit/**`
   - `API_EXTERNAL_URL=https://api.base40.fit`
   - `GOTRUE_DISABLE_SIGNUP=false` — сейчас регистрация на инстансе выключена
     (`disable_signup: true` в `/auth/v1/settings`), новые клиенты не смогут
     зарегистрироваться;
   - хук писем (SMTP не нужен): `GOTRUE_HOOK_SEND_EMAIL_ENABLED=true`,
     `GOTRUE_HOOK_SEND_EMAIL_URI=https://admin.base40.fit/api/auth-email`,
     `GOTRUE_HOOK_SEND_EMAIL_SECRETS=` то же значение, что
     `SEND_EMAIL_HOOK_SECRET` у club40-admin (`v1,whsec_...`);
   - `GOTRUE_RATE_LIMIT_EMAIL_SENT=100`.
     Затем перезапустить сервис auth.
3. **SQL** (Studio → SQL Editor): прогнать `db/selfhosted_storage_urls.sql` —
   переписывает в данных ссылки на аватарки со старого облачного хоста.
4. Проверка: вход кодом в клиентском приложении и ссылкой в админке (см.
   Задачу 2, шаг 7); в DevTools нет запросов к `*.supabase.co`.

# Задача 0. 🔴 Миграция безопасности — ВЫПОЛНИТЬ ПЕРВОЙ

По итогам аудита доступа (2026-08-07) в живой базе открыты дыры, которые
критичны перед массовой раздачей клиентского приложения. Пока эта миграция не
прогнана — любой зарегистрировавшийся клиент может читать чужие данные и
отменять чужие абонементы.

**Что сделать:** Supabase Dashboard → **SQL Editor** → New query → вставить
целиком содержимое файла `db/security_hardening.sql` из репозитория
(ветка с правками; после мержа — из `main`) → **Run**. Миграция идемпотентна,
безопасно запускать повторно. Ожидаемо появятся зелёные `NOTICE ... skipping` —
это нормально.

**Проверка, что сработало (по желанию):** после прогона в SQL Editor выполнить

```sql
select tablename, policyname from pg_policies
where schemaname = 'public'
  and tablename in ('clients','client_memberships','feedback','nps_responses')
order by 1, 2;
```

Должны быть политики вида `clients self or trainer select`,
`client_memberships self or trainer select`, по четыре политики у `feedback` и
`nps_responses` (select/insert/update/delete). Если видишь старые
`clients studio select` / `feedback read all auth` — миграция не прошла,
запусти ещё раз и покажи владельцу ошибку.

Что чинит (детали — в шапке самого файла): утечку всей клиентской базы (PII)
любому вошедшему; чтение/правку чужих отзывов и NPS; IDOR-отмену чужого
абонемента; запуск пакетных простановок статусов клиентом.

**Затем прогнать вторым файлом `db/storage_hardening.sql`** (тем же способом,
SQL Editor → Run). Он закрывает запись/удаление в маркетинговых бакетах
(картинки новостей, абонементов, услуг, фото тренеров/тренировок) — раньше
любой клиент мог их перезаписать или удалить. Требует, чтобы 0a был прогнан
раньше (использует хелпер `is_staff`). Проверка: после прогона в бакетах
должны остаться политики `<bucket> staff insert/update/delete` вместо
`<bucket> auth ...`.

# Задача 2. Письма авторизации — доделать шаги 4–7

Шаги 1–3 (ключ Resend, секрет хука, переменные в Coolify + рестарт) уже
выполнены — **не повторяй их и не пересоздавай секрет** (пересоздание сломает
уже настроенные переменные).

### Шаг 4. Хук включён?

Supabase Dashboard → **Authentication** → **Hooks** → **Send Email Hook**.

- Проверка: хук существует с URL `https://admin.base40.fit/api/auth-email`
  и переключатель стоит **Enabled**.
- Если Enabled уже стоит — иди к шагу 5.
- Если хук есть, но выключен — включи (Enable) и сохрани.
- Если хука нет вовсе (маловероятно) — создай: тип HTTPS, URL выше. ВНИМАНИЕ:
  при создании сгенерируется НОВЫЙ секрет — тогда его нужно скопировать и
  заменить значение `SEND_EMAIL_HOOK_SECRET` в Coolify (club40-admin →
  Environment Variables) и нажать Restart, и только потом включать хук.

### Шаг 5. Длина кода — МЕНЯТЬ НЕ НУЖНО

Supabase не позволяет настраивать Email OTP Length (всегда 6 цифр), и
клиентское приложение уже переведено на 6 ячеек. **Ничего не меняй.**
Можешь только проверить, что OTP Expiration = 3600 сек.

### Шаг 6. Проверка писем (выполни обязательно, даже если 4–5 были готовы)

1. Открой https://app.base40.fit → введи **почту владельца** → «Получить
   код». Должно прийти письмо от `Base40 <noreply@base40.fit>` с
   **6 цифрами и без единой ссылки**. Введи код — вход должен сработать.
2. Открой https://admin.base40.fit → войди той же почтой и паролем владельца.
   Должно прийти **другое** письмо — со ссылкой «Войти в админ-панель», без
   кода. Клик по ссылке = вход.
3. Ключевой критерий: **одна и та же почта в двух приложениях получает разные
   письма**. Если в клиентском приложении пришла ссылка в админку или письмо
   с адреса Supabase — остановись и сообщи владельцу.
4. Письма не в спаме.

Диагностика, если письма не приходят: Coolify → club40-admin → Logs, строки
`[auth-email]`. Аварийный откат: выключить хук в Supabase.

### Шаг 7. Лимиты

Supabase → **Authentication** → **Rate Limits**.

- Проверка: лимит отправки писем ≥ 30/час. Если уже поднят — готово.
- Если стоит маленький (2–4/час) — поставь 100/час.

# Задача 6. 🟢 Миграции под аналитику и новые фичи

Новые фичи (прочие продажи, оплата/скидки/возвраты, заморозка, гигиена данных).
Прогнать в SQL Editor **в этом порядке** (идемпотентно, проверено на локальном
Postgres 16). Требуют, чтобы `security_hardening.sql` был уже прогнан (нужен
`is_staff`).

1. `db/other_sales.sql` — каталог позиций `sale_items` + продажи `other_sales`.
2. `db/sales_payment.sql` — поля оплаты/скидок на `sales` и `other_sales` +
   таблица `refunds`.
3. `db/membership_freeze.sql` — заморозка (лимит в тарифе, статус `frozen`,
   журнал, RPC freeze/unfreeze). Переопределяет `activate_membership_from_sale`,
   поэтому запускать **после** `db/client_memberships_cancel.sql`.
4. `db/booking_hygiene.sql` — единый словарь статусов посещений, автоистечение
   `expire_memberships()`, триггер `last_visit_date`, причины/срок отмены брони.
5. `db/bookings_log_full_reason.sql` — добавляет причину и срок отмены во вью
   «Истории записей» (после 4).
6. `db/booking_waitlist.sql` — лист ожидания: запись в очередь при заполнении +
   счётчик `waitlist_count` (после 4; переопределяет функции записи/отмены).
7. `db/client_profile_backfill.sql` — карточки клиента для тех, кто
   зарегистрировался ДО автосоздания (триггер срабатывает только на нового
   пользователя), плюс функция самолечения `ensure_client_profile()`.
   **Запускать после 8.** Без неё уже зарегистрированные клиенты видят
   «Профиль клиента не привязан к студии» и не могут записаться.
8. `db/client_app_fixes.sql` — исправления по ревью клиентского приложения:
   регистрация создаёт карточку клиента, клиент может править свой профиль,
   матвью статистики закрыта, студия клиента синхронизируется с профилем.
   **Запускать после 7.**
9. `db/review_fixes.sql` — исправления по код-ревью: убрана двусмысленная
   перегрузка RPC, заморозка сама снимается по сроку, возвраты не блокируют
   удаление продажи, корректная ёмкость занятия, `frozen` в статусе клиента,
   простановка неявок ограничена студией. **Запускать последним.**

После прогона можно повесить на pg_cron ежедневно:
`select public.expire_memberships();` и (если уже прогнан stats) обновление
матвью статистики. Функциональность в админке (раздел «Прочие продажи» и пр.)
подтягивается кодом отдельно.
