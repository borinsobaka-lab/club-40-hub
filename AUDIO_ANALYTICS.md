# «Аудиоаналитика» — запись рабочего дня на ресепшене и разбор разговоров

Решение владельца 2026-10-30: речевая аналитика из отдельного проекта
`audio-analitics` (FastAPI + Celery + Redis + Cloudflare R2 + своя админка)
переезжает на портал. Интерфейс — раздел рейки «Аудиоаналитика» в админке,
сервис — в этом же репозитории и на том же сервере (Hetzner, Coolify).
Переносится **только** запись дня и его разбор. Не переносятся: «Скрипты»
(уже на портале — «Скрипты LS», 2026-10-10), CRM (разбор переписок amoCRM и
Wazzup), сценарии звонков, ИИ-помощник скриптов, свои логины и пароли
прежней админки (вход — общий вход портала, права — роли).

## Что делает

1. **Приложение на ресепшене** (`apps/recorder`, Tauri, macOS/Windows) весь
   день пишет микрофон Opus-кусками по 5 минут и отправляет их в сервис.
   Перед началом сотрудник выбирает себя из списка менеджеров; точка
   продажи выбрана один раз при установке. Пауза, пропавший микрофон и
   перезапуск пишутся тишиной — «14:32» в отчёте значит 14:32 на часах
   студии. Микрофон переоткрывается сам, случайное закрытие перехвачено
   двумя вопросами, «Завершить» не теряется без сети, прошлые незакрытые
   смены досылаются при запуске, автозапуск при входе в систему, обновление
   по кнопке (подпись ключом владельца).
2. **Смена** появляется в «Аудиоаналитике» → «Смены» со статусом «Ждёт
   разбора» и ничего не стоит, пока её не разберут кнопкой «Обработать» —
   так не платим за пустые дни, дубли и проверки оборудования.
3. **Разбор** (сервис `services/audio-analytics`): склейка кусков (ffmpeg) →
   поиск речи (Silero VAD; обычно остаётся 2–4 ч из 12) → распознавание
   ElevenLabs Scribe (диаризация, пословные таймкоды; русский, грузинский,
   английский) → Claude: деление дня на разговоры и их тип (продажа,
   консультация, отказ, сервис, личное) → оценка каждого разговора по всем
   активным **метрикам** одним запросом (применима ли, балл по шкале 5/10,
   что хорошо и что плохо с цитатами) → итог смены (главные отклонения,
   рекомендации, предложения по скрипту, удачные моменты). Сервисные и
   короткие (меньше 4 реплик) разговоры по метрикам не оцениваются. Личные
   разговоры классифицируются, но их текст не сохраняется.
4. **Отчёт смены**: итоги, плитки метрик, разговоры с временем на часах
   студии, ▶ проигрывает запись с начала разговора, расшифровка, оценки с
   «согласен / не согласен» (голос — к конкретной оценке; несогласия копятся
   у метрики — очередь на правку её промпта), **договорённости** (одна вещь
   на следующую смену; в следующей смене того же менеджера всплывают с
   вопросом «сделали?»).
5. **Дашборд**: любой показатель за период рядом с предыдущим периодом той
   же длины, по менеджеру и точкам; динамика — отдельный график на каждую
   метрику (шкалы 5 и 10 на одной оси дали бы ложное сравнение);
   стоимость разбора.
6. **Пересчёт**: «Пересчитать» берёт расшифровку прошлого разбора (за
   распознавание второй раз не платим) — после правки метрик или промптов;
   «Распознать заново» — с распознаванием.

## Устройство

| Часть | Где | Что |
|---|---|---|
| Схема | `db/migrations/2026-10-30_audio_analytics.sql` | таблицы `aa_*`, права `audio.*`, RLS, RPC админки; тесты — `db/audio.test.ts` |
| Сервис | `services/audio-analytics/` (Python 3.12, FastAPI) | приём записи из приложения, очередь и разбор, ссылки на аудио, сборки приложения, стирание аудио; свой README |
| Админка | `apps/admin` — раздел «Аудиоаналитика» (`/audio…`) | смены, отчёт, дашборд, договорённости; настройки: метрики и промпты, точки продажи, менеджеры, приложение |
| Приложение записи | `apps/recorder/` (Tauri v2) | запись на ресепшене; README — сборка, ключ обновлений, переезд студий |

**Почему сервис на Python, а не на Bun**, как остальной репозиторий:
пайплайн (Silero VAD на onnxruntime, нарезка звука по сэмплам, разбор
ответов модели) перенесён как есть вместе с тестами — он отлажен на
двенадцатичасовых сменах (память, точность таймкодов, повторы запросов).
Переписывание дало бы те же функции с новыми ошибками.

**Без Redis и Celery.** Очередь — в самой базе: админка ставит смену в
`queued` (RPC `aa_recording_process`), воркер сервиса забирает её
`for update skip locked` и разбирает по одной. API и воркер — один
контейнер (два процесса). Разбор, прерванный перезапуском, воркер при
старте ставит заново сам; «завис» (статус не двигался 3 часа) — админка
разрешает запустить снова.

**Кто что пишет.** Сервис ходит в базу напрямую (`DATABASE_URL`, мимо RLS) и
один пишет смены, сегменты, расшифровки, разговоры, оценки, итоги, сборки.
Админка — через Supabase с RLS: справочники (точки, менеджеры, метрики) —
таблицы, остальное — RPC (`aa_recording_*`, `aa_prompt_save`,
`aa_feedback_set`, `aa_agreement_*`). Удалённая смена или сборка кладёт
папку файлов в очередь `aa_storage_purge` — сервис стирает файлы следом.
Ссылку на аудио браузер получает у сервиса (`/api/staff/audio/<смена>`,
токен входа портала; сервис проверяет право той же функцией базы
`aa_recording_visible`).

**Хранилище аудио** — на диске сервера (том `/data` ресурса в Coolify, по
умолчанию) или в S3-совместимом (прежний бакет Cloudflare R2 подходит):
`STORAGE_BACKEND`. Смена — около 170 МБ за 12 часов. Срок хранения аудио —
`AUDIO_RETENTION_DAYS` (60 дней, как требовала политика прежнего проекта):
сервис раз в сутки стирает звук старых смен, разбор и текст остаются
(пересчёт по новым метрикам по-прежнему возможен, повторное распознавание —
нет).

## Права

Каталог «Пользователей и ролей», блок разделов (сеть):

| Право | Что разрешает |
|---|---|
| `audio.own` — «Аудиоаналитика: свои смены» | смены, где менеджер — он сам (менеджер связан с учётной записью в «Менеджерах»), свой дашборд, «согласен / не согласен», договорённости по своим сменам (итог не ставит) |
| `audio.view` — «все смены» | все смены, дашборд по всем, договорённости — записывает и подводит итог |
| `audio.manage` — «настройки» | всё выше + метрики и промпты, точки продажи, менеджеры, приложение; запуск разбора, принудительное завершение, удаление смен |

У людей вне модели прав — владелец клуба (как в «Аналитике сети»).
Расшифровки — самое чувствительное в разделе: чужая смена для «своих» не
«запрещена», а «не найдена».

## Перенос из прежнего проекта

`python -m cli.import_legacy` сервиса (README сервиса) переносит из прежней
базы точки, менеджеров, смены с разборами, метрики, промпты, отзывы,
договорённости и сборки приложения — с теми же id. Поэтому приложения в
студиях после обновления продолжают работать с той же выбранной точкой.
Аудио: при том же бакете R2 ключи файлов те же; при хранении на диске —
`--copy-audio` копирует файлы из R2.

Переезд студий — одно обновление по кнопке: сборка с новым адресом сервера,
подписанная прежним ключом, выкладывается в **прежнюю** админку
(`apps/recorder/README.md`, «Переезд студий»). После этого прежний проект
можно остановить (разбор CRM и скрипты прежней админки при этом тоже
перестанут работать — их судьба решается отдельно).

## Приватность и право (Грузия)

Аудиозапись в помещении регулируется законом Грузии «О защите персональных
данных» (в силе с 01.03.2024): табличка-уведомление для клиентов, письменное
согласие сотрудников, документированная политика хранения (60 дней) и
ограничение доступа. Формулировки — с юристом. В приложении есть «Пауза»
для личных разговоров.
